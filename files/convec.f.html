Explanation

Purpose. This file finds the convective and radiative regions of a model: the boundaries of each convection zone, without and with overshoot, the edge of the convective core (JCORE) and the base of the convective envelope (JENV), and the radiative regions between them. Its header stresses that overshoot here means "overmixing": overshoot shells are mixed with the convection zone but keep the radiative temperature gradient.

How it fits.

  • Inputs: the arguments LC (convective or not, per shell, from COEFFT via the structure solution), M, and the model (HCOMP, HD, HP, HR, HS, HT), which only OVERSH uses; the overshoot switches LOVSTC, LOVSTE, LOVSTM (core, envelope, intermediate zones) in /DPMIX/.
  • Who calls it: the main program (main.f), MIX, GETW and OVROT.
  • What it calls: OVERSH, which moves the zone edges outward by the overshoot distance.
  • Outputs: MXZON0, NZONE0 (the zones without overshoot), MXZONE, NZONE (with overshoot, after merging zones that overlap), MRZONE, NRZONE (the radiative regions), JCORE, JENV (both before overshoot). MIX uses the zones to treat burning in radiative and convective regions differently; OVROT (which sets the flags LCZ from them), ROTMIX and MIDMOD also loop over the radiative regions; JENV is used throughout the code.

The method.

  1. Scan the shells for runs of convective shells; a run of a single shell is ignored (the test I1.NE.I-1). At most 11 zones: as soon as the 11th is stored, the routine prints "TOO MANY MIX ZONES" (whether or not more follow) and stops the scan.
  2. No zone: JCORE = 1, JENV = M, one radiative region. One zone covering the whole star: fully convective, JCORE = JENV = 1, NRZONE = 0 (MRZONE is left as it was; every reader loops from 1 to NRZONE, so none reads it), and overshoot and merging are skipped.
  3. JCORE is the top of a zone starting at shell 1; JENV the bottom of a zone ending at shell M.
  4. If any overshoot switch is on, call OVERSH, then merge zones whose (overshot) edges now meet, with a message to ISHORT.
  5. The radiative regions: below the first zone, between zones, above the last.

Questions for the experts

  1. An index error. For a radiative region above the last convection zone, the code sets MRZONE(1,2) = M instead of MRZONE(NRZONE,2) = M. When that region is the only one (a convective core under a radiative envelope), the two are the same element and nothing goes wrong. When it is the second or a later one (a radiative surface and at least two radiative regions, e.g. a radiative core, a thin convection zone and a radiative surface), the top region's upper edge keeps an old value and the first region's upper edge becomes M. MIX then burns the shells of the convection zones above the first region one by one, as radiative, before it treats each zone as a unit, and ROTMIX and MIDMOD treat those shells as radiative too (OVROT sets the convective flags after the radiative ones, so its LCZ comes out right). This looks like a bug. KC's check I .GT. 0 in OVROT (2025-05-30, "to avoid runtime error") guards a loop over the same MRZONE, and may be related.
  2. The header's wording. It says JCORE and JENV are "the edges of the surface and central convection zones respectively"; the code makes JCORE the core's edge and JENV the envelope's base (the reverse order).
  3. One-shell zones. A single convective shell is treated as radiative. Is this a deliberate filter against noise in LC?

Review (round 1)
  1. Wrong. Question 1 says the index error (MRZONE(1,2) = M for the top radiative region) affects "stars with a convective core and a radiative envelope". In that case NRZONE is 1 when the line runs, so MRZONE(1,2) is the right element. The error bites only when the top region is the second or a later one (a radiative surface with at least two radiative regions, e.g. a radiative core, a thin convection zone and a radiative surface). Then the first region's top becomes M, so MIX burns the shells of the zones above shell by shell (as radiative) before treating each zone as a unit, and ROTMIX and MIDMOD treat them as radiative too (OVROT, which sets the convective flags last, is not affected). Fix: say so; note that KC's 2025-05-30 check I .GT. 0 in OVROT loops over the same MRZONE (possibly related).
  2. Wrong. Question 2 is garbled ("NZONE is set, but MXZON0 is"). On the fully convective path NZONE, NZONE0 and MXZON0 are all set (one zone, 1 to M); only MRZONE is left as it was, with NRZONE = 0, and overshoot and merging are skipped. All readers loop 1, NRZONE, so nothing reads MRZONE. Fix: state it under the method; drop the question.
  3. Missing. The readers of MRZONE, NRZONE: MIX, OVROT (sets LCZ), ROTMIX and MIDMOD. Fix: add to the outputs.
  4. Unclear. "more prints TOO MANY MIX ZONES": the message is printed as soon as the 11th zone is stored, whether or not more follow. Fix: reword.
