Explanation

Purpose. LABEL_MOD holds the envelope's $X$ and $Z$ of the current run, used to label the output, shared by 6 routines. It replaces COMMON/LABEL/ (MHP via Claude, 10/14/26).

What its variables hold, who sets them, who reads them.

  • XENV0, ZENV0 (REAL*8): set by the main program at the start of each run NK from the namelist arrays XENV0A(NK), ZENV0A(NK), and by RSCALE when the run rescales the composition (RESCAL(2,NK), RESCAL(3,NK); RSCALE then also sets ZENV from ZENV0, "DBG 4/95 bug fix"). Written in the headers of the output by WRTHEAD, WRTMOD and WRTOUT.
  • Initial values 0.7D0 and 0.02D0, moved from PARMIN's DATA XENV0, ZENV0/0.7,0.02/; they are overwritten before any use.

Design. A blanket USE LABEL_MOD; PARMIN still uses the module, though it no longer reads or writes either member (at rp_1 it wrote them to the .short file). The module header says its literals are copied verbatim, but the DATA statement's single-precision 0.7 and 0.02 became 0.7D0 and 0.02D0; harmless, since the defaults are never used, and the two are in no namelist, unlike what the header says.

Changed since rp_1. New file: COMMON/LABEL/ as a module, with its defaults moved from PARMIN (now in double precision); PARMIN no longer writes them.

Imported with a blanket USE, the convention for the conversion.
All 6 files declared this block identically, so the USE imports
exactly the names the declaration already made global in each
scoping unit and cannot change meaning.

The types restate what the implicit rules supplied: L is
LOGICAL*4, I/J/K/M/N are INTEGER*4, everything else REAL*8.
SAVE is explicit rather than relying on module variables being
implicitly saved, which holds only from Fortran 2008 while
ifort Classic predates it.  That matches COMMON's semantics.

2 of the 2 members carry an initializer, migrated
from parmin.f's DATA statements because DATA on a USE-associated
name is rejected.  The literal text is copied verbatim: these
are namelist variables whose DATA supplied a default the
namelist read could override, and a module initializer is
applied once at load time, before PARMIN runs, which is the
same thing.  Rewriting a literal such as 0.9828 as 0.9828D0
would change its stored value, so that is deliberately not
done here; see KNOWN_ISSUES.md issue 23.
