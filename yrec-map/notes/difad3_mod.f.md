## Explanation

**Purpose.** `DIFAD3_MOD` holds the Zahn-type factors of the diffusion-plus-advection treatment of angular momentum (`LDIFAD`), shared by [`SETUPV`](https://github.com/yreclab/yrec/blob/7be4133/src/setupv.f#L3-L467), [`VCIRC`](vcirc.f.md#vcirc), and [`DADCOEFT`](dadcoeft.f.md#dadcoeft). It replaces `COMMON/DIFAD3/` (MHP via Claude, 10/14/26); `JSON` comes from [`DIMENSIONS_MOD`](https://github.com/yreclab/yrec/blob/7be4133/src/dimensions_mod.f#L38-L44). All 21 members are arrays of `JSON`.

**What its variables hold, who sets them, who reads them.**
- `FACD2`, `FACD3`: factors set by `SETUPV`, from which `VCIRC` forms `VESD2`, `VESD3` (`0.2*FACD*WM`, then rescaled by the $`\mu`$-gradient factor); `VESD2`, `VESD3` are read nowhere else.
- `FV0`, `FV1A`, `FV1B`, `FV2A`, `FV2B`: set by `SETUPV` (`FV2B` with the `FACT7` term added); `VCIRC` rescales `FV0`. `FV1A`–`FV2B` are read nowhere: unused? (So are `VESD2`, `VESD3` above.)
- `DSS`, `DGSF`: $`r\,|v_\mathrm{SS}|`$ and $`r\,|v_\mathrm{GSF}|`$, set by `VCIRC`, read nowhere: unused?
- `EV0`, `EV1A`, `EV1B`, `EV2A`, `EV2B`, `ECOD5`, `ECOD6`, `FGEOM`, `ESS`, `EGSF`: read by `DADCOEFT` to build its coefficients (`ESS`, `EGSF` rescaled in place there), but set by no routine, so they keep their initial values (zero in practice, though a module variable without an initializer is formally undefined). The coefficients `ECOD3`, `ECOD4` that DADCOEFT computes from them are then zero ([dadcoeft.f, lines 244–269](https://github.com/yreclab/yrec/blob/7be4133/src/dadcoeft.f#L244-L269)), and DADCOEFT divides by `FGEOM` ([dadcoeft.f, lines 592–597](https://github.com/yreclab/yrec/blob/7be4133/src/dadcoeft.f#L592-L597)). This is [DADCOEFT's suspected bug 1](dadcoeft.f.md#b1) (only with `LDIFAD`, off by default), whose possible fix takes them for the even-grid versions of the `FV*`, `DSS`, and `DGSF` on the model's grid; `VESD2` and `VESD3` may be missing inputs too, and `FGEOM` a geometric factor still to be computed.

**Design.** A blanket `USE DIFAD3_MOD`.

> **Question** ([setupv.f, lines 350–354](https://github.com/yreclab/yrec/blob/7be4133/src/setupv.f#L350-L354), [setupv.f, line 445](https://github.com/yreclab/yrec/blob/7be4133/src/setupv.f#L445), [dadcoeft.f, line 244](https://github.com/yreclab/yrec/blob/7be4133/src/dadcoeft.f#L244), [dadcoeft.f, line 265](https://github.com/yreclab/yrec/blob/7be4133/src/dadcoeft.f#L265), [dadcoeft.f, line 594](https://github.com/yreclab/yrec/blob/7be4133/src/dadcoeft.f#L594)). **Were the `EV*` meant to be the `FV*`?** SETUPV sets `FV0`, `FV1A`, `FV1B`, `FV2A`, and `FV2B`, which no routine reads except VCIRC's rescaling of `FV0`; DADCOEFT reads `EV0`, `EV1A`, `EV1B`, `EV2A`, and `EV2B`, which no routine sets. The names of the two sets differ only in their first letter. Were the `EV*` meant to be the `FV*` mapped onto DADCOEFT's even grid, as the possible fix of [DADCOEFT's suspected bug 1](dadcoeft.f.md#b1) assumes, or meant to be computed some other way? PARMIN's comment of 10/29/26 reads them so ("The mapping of SETUPV's FV* arrays onto the equal grid was never written," [parmin.f, lines 990–998](https://github.com/yreclab/yrec/blob/7be4133/src/parmin.f#L990-L998)); the original code does not say.
