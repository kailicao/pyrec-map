json

Purpose

DIMENSIONS_MOD holds JSON = 5000, the maximum number of shells in a model, the one structural array dimension shared by the whole code (MHP via Claude, 10/15/26). It replaces the statement PARAMETER(JSON=5000) that 108 files repeated at rp_1; it is not a COMMON block.

Who uses it. 144 files: the routines that dimension arrays by the number of shells, and, since 10/20/26, the 36 block modules sized on JSON (such as DEUTER_MOD), which used to declare private copies. The module must be compiled before them (the Makefile says so).

Design

The header explains what stays out: the dimensions of the input tables (such as NUMT, 70 for the OPAL95 opacities and 85 for the ALEX06 tables of Ferguson et al. 2005) differ between tables and stay PRIVATE in each table's module, and scratch bounds such as NMAX stay local to their routines. A file that gains USE DIMENSIONS_MOD must drop its own PARAMETER(JSON=5000).

11C JSON is the maximum number of shells.  It is a property of the
12C code's own arrays, not of any input data file, so one global value
13C is correct by construction: there is no table that could want a
14C different JSON.  It was declared identically as PARAMETER(JSON=5000)
15C in 108 files.
16C
17C This module deliberately holds ONLY dimensions of that kind.  The
18C input-table dimensions do NOT belong here, because the same name
19C carries different values for different tables: NUMT is 70 for the
20C OPAL95 opacities and 85 for Alexander 2006, NT is 57 for the
21C surface-pressure tables and 197 for the OPAL06 equation of state,
22C and NTA/NGA differ between the old and current Allard formats.  One
23C module cannot hold NUMT twice.  Each table module declares its own
24C PRIVATE copy instead, so those values coexist by scope with no
25C renaming -- see KNOWN_ISSUES.md issue 26.
26C

28C 15, 42, 100 and 8000 in five different routines, sizing local
29C workspace.
