A new design for YREC

Stage 2 of the overhaul: KC's coding style applied to YREC at the release rp_1, and an object-oriented framework designed from the code's real responsibilities, as the file notes describe them. Drafted by Claude (Oct 25, 2026) for Kaili Cao; nothing is refactored yet. The style is KC's coding style, with effortless as the model package. Its guide is written for Python; Section 6 says how each of its conventions carries over to modern Fortran, and where a Python interface fits. Where the guide says nothing, the choice made is stated, with its reason.

This design is split into pages, one per component; this page holds its goals, the package layout, the data flow, the migration and the open questions:

1. What the design is for

YREC's physics is mature and validated, and its explanations show a code that works; its structure is what makes it hard to read, to test piece by piece and to extend. Global state: routines share data through 243 COMMON blocks as much as through arguments; the constants alone (/CONST1/) are declared in 93 units, the output units (/LUOUT/) in 88, and PARMIN declares 86 blocks and main.f 60. Settings in COMMON are changed for good in the middle of a run: MIX switches settling off for the rest of the run (LDIFY), HTIMER switches the structure time-step criterion off for the whole job (LPTIME), and ENVINT switches the run to gray atmospheres after one failed Allard lookup (KTTAU = 0). A block that is not declared becomes a silent local: SECULR tests LCODM and CODM without declaring /MAG/. No checked interfaces: every routine is an external subprogram, so argument lists are never checked; MASSLOSS passes MDOT one argument (BL) more than it takes, main.f passes an undefined IU to ENGEB, and REDUCE takes 39 arguments. Procedures that are objects in disguise: state and the routines that use it are tied together only by COMMON and SAVE: QUAD keeps 30 cache slots that the caller must reuse with the same abscissas, RATEXT and LIR depend on the previous call, and each table family (three OPAL equations of state, five opacity families, three atmosphere tables) is a set of reader, set-up and lookup routines sharing hidden blocks. One long main program: main.f runs the Monte Carlo loop, the calibrations, the run cards and the evolution step in one routine with GOTOs across loop levels, and PARMIN is 1,461 lines of defaults, namelist reading, derived settings, file opening and run cards. Duplicated code: the three OPAL equation-of-state versions repeat each routine (ESAC/ESAC01/ESAC06, READCO…, RHOOFP…, T6RINTERP…, EQBOUND…, RADSUB…, QUAD…; GMASS01 and GMASS06 are identical); the second-metallicity tables repeat their routines (GTLAOL2, KURUCZ2, YLLO2D2, YLLO3D2); RATES repeats most of ENGEB, "so a change to one must be copied to the other"; there are seven cubic-spline routines and three tridiagonal solvers; two settling solvers (GRSETT, "retained for backwards compatability", and MICRODIFF); PUTSTORE is "mostly a clone of wrtlst.f and putmodel2.f". Fixed sizes: 123 of the 254 files declare JSON = 5000 shells (the comment in main.f still says to change it "by a global change"), and table sizes are typed into DATA statements (LL95TBL, the KRA lists of READCO and READCOEOS01, the dimensions repeated in five OP95… files). Hard exits and stray output: YREC has no interactive prompts (it reads two namelists and runs unattended), but errors end the program with STOP (for example STOP 9999 in STARIN and ALFILEIN, and a model that fails to converge, which STARIN stops), which would also end any Python process that called it, and several routines write to the terminal at every call (MASSLOSS, MDOT, RSCALE, TAUCAL, BSROTMIX). Dead paths: LBURS is always false, so BURSMIX never runs; the receding-convection-zone block of MIDMOD, the old method of CHKCAL and the output of CHECKJ are skipped; WCZ and four files are never called. The design below gives each piece of state one owner, each family of alternatives one base type, and each choice that users make one place to make it, so that each of these can be fixed once, and so that new physics can be added without editing the solver.

2. The package layout

The design keeps YREC's vocabulary (kind cards, the envelope triangle, HCOMP, levels of the Henyey iteration), so that its users can read the new code. The Fortran package is layered by dependency, from kinds at the bottom to evolve at the top (the tree lists the modules in that order, with capi above them all); a lower module never uses a higher one (the compiler enforces this, since modules cannot use each other in a circle). The Python package sits on top of the compiled library, and drivers/ holds thin, run-specific scripts, as in effortless.

yrec.f90 keeps today's command line (yrec run.nml1 run.nml2) and file outputs, so existing namelists, scripts and the test suite run unchanged. The name capi.f90 and the Python modules are a proposal; their scope is Section 6.3.

3. The classes

Each class is a Fortran derived type with type-bound procedures (Section 6.2 gives the conventions). Signatures are shown in short form: the procedure's header and a docstring of !! lines in NumPy style, with shapes and units; the declarations they imply follow Section 6.2 (intent, kind dp unless stated, ierr an integer error code, 0 for success). m is the number of shells, nsp = 15 the number of species in HCOMP (in the order the code prints: $X$, $Y$, $Z$, ³He, ¹²C, ¹³C, ¹⁴N, ¹⁵N, ¹⁶O, ¹⁷O, ¹⁸O, ²H, ⁶Li, ⁷Li, ⁹Be). Arrays are allocated to m, not to JSON.

Classes mirror the data, from the whole job down to the piece processed at a time:

Run            # the job: Config, physics, run cards; replaces main.f
├── Track      # one run card: a sequence of models
│   ├── Star       # one stellar model; holds ShellPhysics, EnvelopeSolution
│   └── Step       # one evolutionary step; holds StepStart
└── Physics    # microphysics, set up once: Eos, opacity, atmosphere,
               # nuclear, convection; shared by every Track

4. Data flow

A run goes through the new classes in the order of main.f today; each step names the code it replaces.

  1. Start. drivers/yrec.f90 reads the two namelist paths from the command line (GETARG today) and calls Run%init: Config%read_namelists and Config%derive (PARMIN, REMAP), Logger and TrackWriter open their files, and Physics%setup reads the tables (SETUPS).
  2. Calibration set-up. If the configuration asks for one, Run allocates a SolarCalibr, StarCalibr or MonteCarlo (SETCAL, SETSCAL, the Monte Carlo loop).
  3. Tracks. For each kind card (DO 200 NK), Run%run creates a Track; Track%start reads or keeps the model through a ModelFile and rescales it (STARIN, RSCALE), finds the zones (FINDSH), writes the headers (WRTHEAD), copies the model to the ILAST file when the helium flash is followed (LKUTHE, WRTLST; MAIN question 8) and asks the TimeStepper for the first step (HTIMER).
  4. Steps. Track%run repeats Step%run (DO 100 MODELN) until Track%done; each Step%run:
  5. lets PulsationWriter decide on this model's pulsation output (PDIST), and copies the model into StepStart (/OLDMOD/ today);
  6. if the model ages, MassLoss%apply (MASSLOSS), then CompositionStep%run (MIX), and advances the age;
  7. Rezoner%rezone (HPOINT);
  8. guesses the new structure from the rates of change in StepStart, and, for the light elements, has LightElements compute the rates at the start of the step (LIRATE88, mode 1);
  9. calls StructureSolver%solve at levels 1 to 3 (CRRECT), with SurfaceBC rebuilt at level 2, and stores the rates of change for the next guess; on divergence it returns an error, which ends the run as today (label 15; Section 3.12);
  10. then, ITDIF1 times with rotation (once without), restoring the start-of-step composition and $j$ before each repeat: level 4 of StructureSolver%solve, the convergence test, ConvectionZones%homogenize (MIXCZ), RotationStep%run and Distortion%factors (GETW, FPFT);
  11. ConvectionZones%find_shell (FINDSH); the light elements, without rotational mixing: ConvectionZones%find (CONVEC), the rates at the end of the step and the burning (LightElements, LIRATE88 mode 2, LIBURN); after a change of mass, Rezoner%absorb_envelope and Distortion%factors again (GETNEWENV, FPFT);
  12. TimeStepper%next_dt (HTIMER), with the floor on the final step before ENDAGE;
  13. TrackWriter writes the model (WRTOUT), with the analyses it asks for; a StarCalibr's after_model may end the track (CHKSCAL).
  14. End of a track. StoreFile%write if asked (PUTSTORE); a SolarCalibr's check decides whether another cycle runs (CHKCAL), and KTTAU and LPTIME return to their configured values for the next cycle (in the design, a new AtmosphereSwitch and TimeStepper).
  15. End of the job. Calibration summaries, and the Monte Carlo output (WRTMONTE); Run%clear. The driver, not the library, ends the program, with a nonzero exit code if ierr is not 0.

In code, the step reads as its outline:

subroutine step_run(self, ierr)
    !! One evolutionary step (main.f, DO 100). ierr : 0, or STEP_DIVERGED
    !! for the track to cut the step and retry.
    class(Step), intent(inout) :: self
    integer, intent(out) :: ierr
    type(Track), pointer :: tr; tr => self%track  ! Shortcut.

    ! Save the model at the start of the step.
    call tr%star%copy_to(self%start)
    ! Mass loss and composition, if the model ages.
    if (self%dt > 0) then
        call tr%mloss%apply(tr%star, self%dt, ierr); if (ierr /= 0) return
        call tr%comp%run(tr%star, self%start, tr%zones, self%dt, ierr)
        if (ierr /= 0) return
    end if
    ! Rezone, guess, and solve the structure at four levels.
    ...
end subroutine

7. Migration

7.1 The benchmarks

Stage 3 of the overhaul refactors against benchmark data. YREC has it: the development branch carries a test suite of 298 cases (about five hours), a 17-case targeted set extended with cases for the path being changed (F90_CONVERSION_PLAN.md, Validation protocol), a comparison of output files with configurable rules for lines to ignore, and a rebaseline protocol (REBASELINE_PROTOCOL.md, rebaseline.py) for changes that are meant to change results. Two cautions from its KNOWN_ISSUES.md: the reference outputs are not under version control (issue 32, open), and on Oct 20, 2026, 296 of the 298 cases passed (issues 31 and 36). So the overhaul first freezes and archives its own reference set, made from its starting commit, with the failing cases recorded. It then uses the same protocol, with three levels of check:

  • Identical output for a step that only moves code (a routine into a type, a block into a component): the targeted set, and the full suite at the end of each stage.
  • Point comparisons for a merged family (one OpalEos for three releases, one spline routine for seven): the new and old routines evaluated on the same grid of $(\log T, \log\rho, X, Z)$, or on the same random inputs, agreeing to round-off; then the targeted set.
  • A rebaseline, each in its own commit with its reason, for every change of behavior: a bug fix the experts confirm (the questions on each file's page), or a decision of Section 8. A restyle and a change of behavior never share a commit, as the guide asks.

7.2 The order

From the bottom of the layering to the top, so that each step builds on tested types:

  1. Kernels. kinds, constants, numerics, odeint: merge the duplicate splines, solvers and interpolators, with unit tests on exact cases; then point comparisons against each routine they replace.
  2. Settings. Config and KindCard replace PARMIN's blocks; the namelist echo in the .short file must stay the same. Until the last routine that reads a block (or development's module) is converted, Config%derive also fills it, so that the code still runs after this step. Logger replaces the writes to ISHORT.
  3. Physics, family by family. The equation of state, the opacities, the atmospheres, the nuclear rates, convection. Each family first gets its type behind the old call (a thin wrapper keeps the old routine's name and arguments), so the rest of the code does not change; the wrappers go when their callers are converted.
  4. The model and its files. Star, StepStart, ModelFile: a model read and written again must give the same file.
  5. The structure. EnvelopeIntegrator with OdeRhs (which ends the QENV/QATM constraint, Section 7.3), SurfaceBC, StructureSolver, Rezoner, TimeStepper.
  6. Composition, settling, rotation, mass loss.
  7. The run. Run, Track, Step replace main.f; then the calibrations.
  8. The interfaces. The executable reads the same namelists and writes the same files throughout; capi.f90, the Python package's in-process part and UserPhysics come last, once nothing calls STOP.

Each step ends with the targeted set; each stage (one numbered item) with the full suite.

The QENV/QATM constraint. Development's KNOWN_ISSUES.md (issue 7) records that the blocks serving QENV and QATM cannot become arguments, because the two are passed as EXTERNAL derivative routines to BSSTEP and MMID with a fixed argument list; /QENVMIX/ exists only to relay CMIXL to QENV. In the design the derivative is a type-bound procedure of an OdeRhs extension (Section 3.1, EnvelopeRhs), which carries $X$, $Z$, the mixing length and a pointer to the physics as components, so the constraint and the relay block both go.

8. Open questions

Each question is tagged by who answers it: Team, the code's team (its authors and developers), or KC.

  1. [Team] The base. Refactor from rp_1, as the notes describe it, or from the development branch, which has removed nine obsolete options and converted every COMMON block to a module? Proposal: development, after its open issue 29 (no procedure has an explicit interface; issue 27, the dependencies between modules, was resolved on Oct 20) is settled with its developers, since the overhaul would otherwise redo their conversion.
  2. [KC] Working with YREC's developers. The development branch has its own plan (F90_CONVERSION_PLAN.md, stages 0–5, all done). Should this design be proposed to them as the next stages, and who decides on the interfaces they will maintain?
  3. [KC] The language. Decided for now (Oct 25, 2026): Python first and modern Fortran last, the route on the Python version's overview, so this design is the last stage's target, reached through pyrec; Section 6.1 keeps the first sketch's reverse order for comparison. Still open: is the in-process interface wanted, beside the existing yrec package that runs the executable (Section 6.3)?
  4. [Team] Changes of behavior the design would make, each kept behind a flag that gives today's results until decided: the atmosphere chosen per model after an Allard failure rather than gray for the rest of the run (ENVINT question 9); settling switched off by MIX only for the current track; the ⁷Be screening of RATES against ENGEB (RATES question 5); SUNL against CLSUN in the Monte Carlo runs (Section 5). And one the design does not make: today a model that fails to converge ends the run (STARIN stops at label 15, although main.f's comment speaks of time-step cutting); should Track%run instead cut the step and retry, and with what limit?
  5. [Team] What to drop. Code that never runs or is never called: BURSMIX and BSROTMIX (LBURS always false), the receding-convection-zone block of MIDMOD, the old method of CHKCAL, WCZ, PUTYREC7, SPLINNR, SPLNR, and the LNUTAB block of main.f. Development has already removed WCZ, SPLINNR and SPLNR (commit da1887a) and kept PUTYREC7 on purpose, at its developers' decision (KNOWN_ISSUES.md, issue 24). Proposal: drop the others, each with a line in the commit, unless an expert wants one back; keep PUTYREC7 as development does.
  6. [Team] Two settling solvers. Keep GRSETT ("retained for backwards compatability") as GrsettSettling, or keep only MICRODIFF?
  7. [Team] Several interior opacity tables at once (SETUPOPAC question 1): the design allows an array of them in OpacityBlend; is that wanted, or one table per run?
  8. [Team] Output files. Keep every format byte for byte through the refactoring (the proposal, so that the test suite can compare files), and change formats only afterwards?
  9. [Team] Which hooks first. The six of Section 6.5 cover the additions found in the notes; which do YREC's users need first, and should spot evolution be the first one to use them?
  10. [Team] Names. Keep YREC's names (HCOMP, HTOLER, ATIME) in the types and namelists, as this design does so that YREC's users can read the new code, or move to the "more intuitively named" ones that REMAP already accepts (TIME_…, TOL_…)?
Review (round 1)

What was checked, and held

  • COMMON-block map (6.4). A script over callgraph.json finds 243 distinct blocks; the map names each exactly once, with none missing and none extra. The counts in Section 1 hold: /CONST1/ in 93 units, /LUOUT/ in 88, PARMIN 86 blocks, main.f 60.
  • Routines replaced. Every unit link resolves to a unit in the call graph, and every unit of the call graph is named on the page (BLOCK_DATA through blkdta000.f).
  • Code claims spot-checked and right: REDUCE takes 39 arguments; QUAD's 30 cache slots; MIX sets LDIFY = .FALSE., HTIMER sets LPTIME = .FALSE., ENVINT sets KTTAU = 0; SECULR tests LCODM, CODM without /MAG/; LBURS = .FALSE. in GETW; ENGEB called with the undefined IU in main.f; STOP 9999 in STARIN and ALFILEIN; /ALATM04/ holds only DUMMY1–DUMMY4; GMASS01 and GMASS06 differ only in name, case and a blank line; PARMIN is 1,461 lines; GETW's substep count is the minimum of the two ceilings; CRRECT's damping FCORR = min(1, FCORR + FCORRI); /QENVMIX/ is not in rp_1 (it is development's).
  • The other branches. Dates and commit counts hold (development Oct 20, 246 ahead of rp_1; main Oct 11, 176; spotevol Sep 24, 162; yrec_2026_release Sep 16, 154; modern Apr 26, 2025, 41 ahead and 121 behind, all 41 by Kaili Cao; jvs0210 Oct 2, 2025, 0 ahead and 36 behind). On development: F90_CONVERSION_PLAN.md, KNOWN_ISSUES.md, REBASELINE_PROTOCOL.md, rebaseline.py, wrappers/ exist; no COMMON statement is left in src/ (issue 37, resolved Oct 20); all 284 .f files contain IMPLICIT NONE; the full suite is 298 cases, "about five hours", with a 17-case targeted set (plan, Validation protocol); the CALL MDOT mismatch was fixed in b3b0601; docs/source/python_package.md documents pip install yrec and yrec.run_parallel; YREC_INPUT is used. Issues 7 (QENV/QATM) and 11 (ENVSTRUCT, ATMSTRUCT held for output) say what the page says.
  • Style. The conventions of the guide carry over sensibly (6.2): init/run/clear, …Base for private bases, ierr for errors, UPPERCASE parameters with the case-insensitivity caveat, hooks that do nothing in the base, one Config read once. The tree is at most 79 characters wide.

Findings and proposed fixes

Wrong

  1. A divergence does not cut the step today; it ends the run. Sections 3.12 and 4 (step 5) say "Track%run cuts the step and tries again (label 15)". In rp_1, label 15 calls STARIN with LARGE set, and STARIN writes "MODEL FAILED TO CONVERGE" and STOPs (starin.f, lines 137–146), despite main.f's comment "STARIN called here for timestep cutting". (The main.f note, Steps 2, repeats the comment's claim; the starin.f note is right.) Fix: say that today a divergence ends the run; Step%run returns STEP_DIVERGED, and Track%run ends with that error, as today; cutting and retrying is a new behavior and goes into Section 8 (question 4).
  2. The MDOT mismatch is in massloss.f, not main.f. Section 1: "main.f passes MASSLOSS one argument more than MDOT takes". massloss.f (line 176) calls MDOT with BL first; MDOT has no such argument. Fix: "MASSLOSS passes MDOT one argument (BL) more than it takes".
  3. "Every file declares JSON = 5000" (Section 1, and Section 5 "in every file"): 123 of the 254 files do. Fix: "123 of the 254 files".
  4. StarCalibr checks every model, not a finished track. main.f calls CHKSCAL inside the model loop (line 975, on even kind cards after the first model) and may end the track there (GOTO 200); only CHKCAL runs at the end of a track. Section 3.13 (check "from a finished track's TrackSummary") and Section 4 (step 5) say otherwise.
