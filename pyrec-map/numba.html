Writing a Numba family

Part of A new design for YREC. How to write a family whose hot paths run compiled, from the lessons of the Fortran-tracking pyrec's speed work (pyrec's README, Conventions: Numba). A family in plain Python works too, but slows every compiled chain that calls it (The compiled tree).

How a family's kernel joins a chain

Numba compiles a chain of kernels together only if every kernel in it is compiled and known when the chain compiles: A compiled kernel cannot call a Python object chosen at run time. pyrec's chains (the solver's loop over the shells and the envelope's integration) are pyrec's own kernels, spread over several modules, and each calls a family through a module global named for the call: opacity_point, eos_point, convection_point, network_point and network_serves, and the atmosphere's atmosphere_point and envelope_point. In the Fortran-tracking pyrec each global is bound to pyrec's own kernel.

When families are installed, the chains are generated: For each chain module, a new module is written that copies the original's namespace, binds each global to the installed family's static method, imports the chain's other generated kernels, and redefines the chain's kernels from their own source, decorators kept, so that Numba compiles them against the new bindings. The rest of the module (its constants, its other kernels) is shared, and the kernels' source, with its comments citing the Fortran's lines, stays where it was. The generated files go to Numba's cache folder; a file is rewritten only when its text changes, and its text holds a hash of every source it depends on, so that an edit anywhere in the chain's package recompiles the chain (Numba's own cache does not see a callee's change).

When an installed family's kernel is plain Python, the chain is generated without its decorators and runs as Python, with a PlainFamilyWarning.

A worked example: the opacity

The default opacity's hot path is one static method over one point, compiled with pyrec's options, inline='always', and no reference counting. It calls pyrec's getopac kernel, unchanged, on the family's data:

class Opacity(OpacityBase):
    @staticmethod
    @accel.njit(inline="always", _nrt=False)
    def point(log_density, log_temperature, x, z, ionization, data):
        d = data
        return _getopac_nb(log_density, log_temperature, x, z, ionization, d.tmolmin, d.tmolmax, d.lcondopacp,
                           d.capalex06, ..., d.guess)

    def kernel_args(self):            # the settings, tables, and saved guesses, as one named tuple
        return _getopac.data_in(self._ga, self._guess)

The same mechanism, for one function, evaluates the family without a model: OpacityBase.__call__ writes a loop over the points as plain Python with the kernel as a parameter, and generates from it a compiled loop with the parameter bound to Opacity.point:

def _grid_body(opk, log_density, log_temperature, x, z, fxion, data, served, out, status):

        if served[i]:
            o, ol, qod, qot, st = opk(log_density[i], log_temperature[i], x[i], z[i], fxion, data)
            out[0, i] = o
            ...

f = make_chain(_grid_body, {'opk': type(self).point})    # compiled, opk bound to Opacity.point
f(dl, tl, xx, zz, fx, data, served, out, status)

A plain family runs the same loop as Python, with the warning. On a grid of 91 × 141 points at the ZAMS surface's composition, the compiled family took 1.2 µs a point; a plain-Python subclass (point = Opacity.point.py_func) took 4.6 µs, since its Python point still calls getopac's compiled kernel, paying one call from Python per point; both gave the same bits as pyrec's getopac called point by point (The pilot: opacity).

Kernels

  • Module-level functions or static methods that fill preallocated arrays given to them; nothing is allocated inside a hot kernel, and work arrays are passed in (State, The three homes).
  • No reference counting: Every kernel on a chain sets _nrt=False itself; such a kernel fails to compile if anything inside it allocates, which is how an allocation is caught.
  • Tiny functions called millions of times are compiled with inline='always' (it doubled a chain's speed in a microbenchmark).

Passing data

  • Named tuples of arrays are read fast, without reference counting. Numba's structrefs are not used (their fields need reference counting: an EOS 2–3 times slower), nor is jitclass.
  • Run-time settings reach kernels as arguments, never as module globals: Numba bakes a global's value into the compiled code, and the disk cache keeps stale values. (The families' kernels bound as globals at generation time, above, are the exception: They are code, not settings.) A family's settings, tables, and saved state go in its kernel_args() tuple.

Compiling and the cache

  • The options: cache=True, no fastmath, error_model="numpy" (pyrec's accel.njit); fastmath is left off since it would change the bits.
  • The disk cache: A change to a callee does not always invalidate its caller's cache, so the cache is cleared after an edit anywhere on a chain; the generated chains hash their sources for the same reason.
  • Thread ids: numba.get_thread_id(); the private one breaks caching.

Checking a family

Each default family was checked three ways, and a new family can be checked the same way against the default:

  • Without a model, on a grid: the family's __call__ against pyrec's routine called point by point, byte for byte (the opacity and the EOS on 91 × 141 points of $\log T$ and $\log\rho$ (nominal for the EOS, which takes pressure), the network on 5,187 points at each of two compositions, the convection's gradient on 2,192 points, the envelope's integrand on 1,907), compiled and as a plain-Python subclass.
  • In a whole run: the 1 M☉ ZAMS case with the family's kernel bound into the generated chains, every output file byte-identical to YREC's.
  • In tests of the family alone (pytest), from recorded calls of pyrec's routines, with no whole run.

A family that is meant to change results is compared with the default on the same grid, and its changes are a deliberate change of bits.
